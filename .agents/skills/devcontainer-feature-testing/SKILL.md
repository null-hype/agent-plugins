# Devcontainer Feature testing

Read [the testing guide](references/test.md) before changing test layout, scenario configuration, or execution. It is a snapshot of the [user-specified upstream guide](https://raw.githubusercontent.com/teslamotors/devcontainers-cli/refs/heads/main/docs/features/test.md), retrieved 2026-10-15.

Mirror `src/<feature>` with `test/<feature>`. Default assertions belong in `test/<feature>/test.sh`. A key in `test/<feature>/scenarios.json` names `test/<feature>/<scenario>.sh`, which the CLI executes inside the built container. Additional build files belong in `test/<feature>/<scenario>/`; the CLI copies their contents into the generated `.devcontainer` directory. Resolve Dockerfile and context paths from that generated layout, not from the repository root. The feature test files are not necessarily present in the build context: put build inputs in the scenario directory and inspect the generated context before relying on COPY paths.

Use scenario configuration and its build directory to prepare dependencies; keep assertion scripts focused on exercising the installed feature and checking results. Shared fixtures and helpers may stay at feature scope. A scenario directory is needed for additional build files, not mandatory for every image-only scenario. Use `test/_global` for composition scenarios not tied to one feature.

A test passes when the container builds and its assertion script exits zero. `dev-container-features-test-lib`, `check`, and `reportResults` are optional conveniences; their absence is not a convention violation.

Run the affected scenario through the CLI, for example:

```sh
npx --yes @devcontainers/cli features test -f rails-cases --filter yjit-always-available --skip-autogenerated --skip-duplicated .
```

Use `--global-scenarios-only` for global scenarios. Check the installed CLI's help for flags. In this Codespaces setup, the Docker daemon sees container `/tmp` as `/mnt/containerTmp`; when that mapping exists, use `TMPDIR=/mnt/containerTmp` so generated bind mounts resolve.

For Rails browser replays, CI exports a HAR into the selected case directory before feature tests run; see `test/rails-cases/README.md`. Preserve reviewed recordings and expectations. Missing HARs or failed container builds are setup failures, not evidence that assertions passed or failed. Report the actual command and distinguish build, assertion, and unavailable-evidence outcomes.
