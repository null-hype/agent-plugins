# CIT-270: snapshot diff, Rails upgrade to 7.x

Built the container before and after upgrading Rails from a pre-7 version
(6.1.7) to 7.x (7.0.0 -- the exact release where the default variant
processor changed), restic-diffed the two root filesystems, and recorded
what shows up for libvips and Active Storage. Method, tooling, and results
below; everything referenced lives under [`cit-270/`](./cit-270).

## Build

`cit-270/Dockerfile` takes a single `RAILS_VERSION` build arg and
is otherwise identical between the two builds (same base image
`ruby:3.0-bullseye`, same apt line, same generation flags) -- the goal is to
isolate the Rails-version bump as the only intentional variable. Concretely:

```
docker build --build-arg RAILS_VERSION=6.1.7 -t rails-cit270:6.1.7 .
docker build --build-arg RAILS_VERSION=7.0.0 -t rails-cit270:7.0.0 .
```

Both apps are generated with `rails new . --skip-git --skip-test
--skip-javascript --database=sqlite3` (not hand-written), then
`bin/rails active_storage:install && bin/rails db:prepare`. `--skip-javascript`
is the one deliberate omission: Rails' default JS tooling changed between
6.1 (Webpacker) and 7.0 (importmap-rails) for reasons unrelated to Active
Storage/libvips, and leaving it in would bury the signal this fixture is
after in unrelated churn. Two build-environment compatibility fixes were
needed to get *either* version running at all under this Ruby/Debian combo
(documented inline in the Dockerfile) and were applied identically to both
builds so they don't become part of the measured diff:

- `concurrent-ruby` pinned to `1.3.4` (both globally and in each generated
  Gemfile) -- newer concurrent-ruby releases dropped an implicit stdlib
  `logger` require that 6.1/7.0-era ActiveSupport depends on.
- `bullseye-security` dropped from `/etc/apt/sources.list` -- that suite is
  past its support window and its Packages index now advertises versions
  its pool no longer serves.
- Spring disabled (`DISABLE_SPRING=1`) -- it preloads the app in a
  background process, which doesn't fit a one-shot `docker build` RUN layer.

Generated app trees (with `tmp/`, `log/`, `storage/`, and the sqlite3 db file
stripped -- pure build-run cache/data, not part of what Rails generates) are
committed at [`generated-apps/6.1.7/`](./cit-270/generated-apps/6.1.7) and
[`generated-apps/7.0.0/`](./cit-270/generated-apps/7.0.0) for inspection
without rebuilding.

## Diff method

Each image's full container filesystem was exported (`docker create` +
`docker export | tar -x --numeric-owner`) and backed up into a disposable
local restic repo under the **same literal path** for both snapshots
(`.../rootfs/snapshot-target`, populated with one version's export at a
time) -- restic diffs by tree position, so backing up under different
directory names would have made every file read as "removed" + "added"
rather than showing real content changes. Repo, extracted rootfs, and
password are all scratch-only, not committed.

```
restic backup --host rails-fixture --tag rails-6.1.7 .../rootfs/snapshot-target   # (6.1.7 export in place)
restic backup --host rails-fixture --tag rails-7.0.0 .../rootfs/snapshot-target   # (7.0.0 export in place)
restic diff <snap-6.1.7> <snap-7.0.0>
```

Full raw output (13,489 lines, paths normalized to drop the scratch prefix):
[`restic-diff-6.1.7-to-7.0.0.txt`](./cit-270/restic-diff-6.1.7-to-7.0.0.txt).
Headline stats: 5,174 files new, 5,432 removed, 619 changed. Most of that
volume is exactly what you'd expect from a Rails major-version bump on a
freshly generated app -- different gem versions across the board (every
Rails component gem moves together), not anything libvips/Active-Storage
specific. One build artifact inflates the noise further and is worth naming
rather than hiding: `gem install rails -v X` (for the `rails new` command
itself) and the generated app's own `bundle install` share the same
`GEM_HOME`, so each image actually contains **two** copies of most Rails
gems side by side (e.g. both `activestorage-6.1.7` *and*
`activestorage-6.1.7.10`, the latter being the one Bundler.lock actually
uses) -- a byproduct of this build's gem layout, not of the Rails-version
upgrade. Grep past the patch-version suffix when reading the raw diff.

## What actually shows up for libvips

**Nothing installs libvips, at either version.** No `.so` file, no apt
package, no `ruby-vips` gem, no `image_processing` gem appears anywhere in
either image. Grepping the full diff for `vips` (case-insensitive) returns
exactly two lines, both the same file at its two patch versions:

```
+ /usr/local/bundle/gems/activestorage-7.0.0/lib/active_storage/analyzer/image_analyzer/vips.rb
+ /usr/local/bundle/gems/activestorage-7.0.10/lib/active_storage/analyzer/image_analyzer/vips.rb
```

That file is *framework* code shipped inside the activestorage gem itself
(present because it's part of the gem, not because anything activated it) --
it is not evidence that vips is running. Both Gemfiles generated by `rails
new` ship the same line, commented out, unchanged across the version bump:

```ruby
# gem "image_processing", "~> 1.2"
```

Neither Gemfile.lock includes `image_processing`, `mini_magick`, or
`ruby-vips` at either Rails version -- variant processing is opt-in at both
6.1 and 7.0, identically. This reframes the finding from "the app starts
using vips" to something sharper: **the same one-line Gemfile change
(uncommenting `image_processing`) reaches for a different native library
depending on which Rails version generated the app**, and nothing in either
generated app tree says so.

## What actually shows up for Active Storage

The processor default does change -- confirmed directly in the shipped gem
source, not inferred. `railties-7.0.10`'s
`lib/rails/application/configuration.rb`, inside the `when "7.0"` branch of
`load_defaults`:

```ruby
if respond_to?(:active_storage)
  active_storage.video_preview_arguments = ...
  active_storage.variant_processor = :vips
  active_storage.multiple_file_field_include_hidden = true
end
```

`activestorage-6.1.7.10`'s `lib/active_storage.rb` sets the framework-wide
fallback identically at both versions (`mattr_accessor :variant_processor,
default: :mini_magick`), and `engine.rb`'s initializer at both versions
reads `app.config.active_storage.variant_processor || :mini_magick` --
identical code. The only thing that differs is *what's already sitting in
`app.config.active_storage.variant_processor`* by the time that line runs:
`nil` for a 6.1-defaults app (falls through to `:mini_magick`), `:vips` for
a 7.0-defaults app (set three initializer-lines earlier, per the `when
"7.0"` block above).

**This confirms the asymmetry flagged as the strongest finding this fixture
could produce (recorded before this run):** the *only* place this change
appears anywhere in the fixture's own two generated app trees is a single
version-number token, `config.load_defaults 6.1` vs `config.load_defaults
7.0`, in `config/application.rb` (confirmed -- `grep -rn variant_processor`
across both `generated-apps/` trees returns nothing at all). There's a
second, more visible surface for the *same* setting: `railties-7.0.10`
ships a generator template,
`generators/rails/app/templates/config/initializers/new_framework_defaults_7_0.rb.tt`,
with the line `# Rails.application.config.active_storage.variant_processor =
:vips` spelled out (commented, opt-in) -- but that template is only written
into an app that upgrades in place via `bin/rails app:update` while pinning
`load_defaults` below 7.0; it is not part of what `rails new` generates, and
neither generated-apps tree here has it. So the *safer* upgrade path (in
place, one default at a time) is the one that surfaces this change in a
file a reviewer might read; the *fresh app* path -- what this fixture
built -- flips it with zero application-level trace. That asymmetry is the
mechanical point this fixture set out to demonstrate.

Two things this fixture does **not** establish, matching the earlier
prediction: `storage.yml`'s diff is pure comment-wording churn, not a
service-config or trust-boundary change; and no CWE-1188 finding is
constructable from this diff alone -- the actual vulnerability
(CVE-2026-66066) requires the app to have opted into `image_processing`
*and* installed libvips *and* fed it untrusted uploads, none of which a
fresh `rails new` does. That gap between "the default silently changed" and
"the vulnerable configuration exists" is exactly what CIT-271's free agent
is being asked to notice or miss.

  fix away.
