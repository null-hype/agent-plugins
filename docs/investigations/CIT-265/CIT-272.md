# CIT-272: snapshot diff, libvips upgrade adding the untrusted flag

Builds one container at libvips **8.12.2** and one at **8.13.0**, then
restic-diffs the two root filesystems. 8.13.0 is the first release that
contains libvips commit
[eba9ec0](https://github.com/libvips/libvips/commit/eba9ec0dd71bc2e0a4c14bf23ac9b0516016be61)
("Add a way to disable less well tested operations", 2022-04-11). In a clone
of `libvips/libvips`, `git tag --contains eba9ec0` starts at
`v8.13.0-rc1`/`v8.13.0`, and eba9ec0 is not an ancestor of `v8.12.2`, the
last 8.12 release. Everything referenced lives under [`cit-272/`](./cit-272).

This fixture holds edge **E5** from the CIT-280 review: the dependency ships
a safety control. CIT-277 couldn't hold it, because its image runs apt's
libvips 8.10.5.

## Build

[`cit-272/Dockerfile`](./cit-272/Dockerfile) is one Dockerfile built twice
with `--build-arg LIBVIPS_VERSION=8.12.2` and `=8.13.0`. The build context is
`docs/investigations/CIT-265/`, so the Dockerfile can reach `cit-277/`.

- **Shared layers come before the ARG.** Both builds reuse them from the
  build cache (`CACHED` in both build logs), so they are byte-identical:
  - `ruby:3.0-bullseye`
  - apt build deps and ImageMagick. No apt libvips, unlike CIT-277.
  - CIT-277's upgraded `after` app (Rails 7.0.10, `load_defaults 7.0`,
    `image_processing` 1.14.0, `mini_magick` 4.13.2, `ruby-vips` 2.3.0),
    installed from its committed `Gemfile.lock`.
- **The only per-build layer** downloads the libvips release tarball
  (sha256 pinned), runs `./configure`, `make` and `make install`, all with
  defaults, then `ldconfig`.
- **Both versions are built with autotools.** Both tarballs ship a generated
  `configure`. 8.13.0 also ships `meson.build`, but 8.12.2 has no meson
  support, and meson would install to a different lib directory.
- **Both images have the same feature set.** `vips --vips-config` differs on
  one line, which is only reworded (8.12.2 prints `quantisation to 8 bit:
  yes`, 8.13.0 prints `selected quantisation package: imagequant`). Every
  loader backend is present in both: magick6, poppler, rsvg, openslide,
  matio, cfitsio, OpenEXR, openjp2, heif and the rest. See
  `cit-272/vips-config-*.txt`.
- **Each image has exactly one libvips.** `ldconfig -p` shows only
  `/usr/local/lib/libvips.so.42`. Inside the app,
  `ruby -e 'require "vips"; puts Vips.version_string'` prints `8.12.2-…` in
  one image and `8.13.0-…` in the other.
- **No `bin/rails db:prepare`, unlike CIT-277.** `Bundler.require` loads
  ruby-vips, which dlopens `libvips.so.42` at boot, so the step fails before
  the libvips layer exists. Running it after that layer would add a
  per-build sqlite file to the diff. CIT-278 should run it at container
  start.

Build time on this box (4 CPU): about 2 minutes per libvips compile.

## Diff

The method is the same as CIT-270 and CIT-277:
1. `docker create` a container from each image and `docker export` it.
2. Extract with `tar -x --numeric-owner` to the same literal path.
3. Back up each tree into a disposable restic repo.
4. Run `restic diff`, with the scratch prefix stripped.

The full output is in
[`restic-diff-8.12.2-to-8.13.0.txt`](./cit-272/restic-diff-8.12.2-to-8.13.0.txt)
(127 lines):

```
Files:          12 new,    12 removed,    93 changed
  Added:   67.330 MiB
  Removed: 65.818 MiB
```

**Every path in the diff is libvips-owned, except `/var/cache/ldconfig/aux-cache`.**
There are no Rails, gem, log, sqlite or bootsnap entries, so none of the
noise CIT-280 had to filter from CIT-277. By area:

| Area | Entries | What |
| --- | --- | --- |
| `/usr/local/bin` | 6 | `vips`, `vipsedit`, `vipsheader`, `vipsthumbnail` modified; `vips-8.12` → `vips-8.13` |
| `/usr/local/include/vips` | 51 | headers, incl. new `VRegion8.h`, removed `soname.h` |
| `/usr/local/lib` | 10 | `libvips{,-cpp}.so.42.14.2` → `.42.15.0`, `.a`, `.la`, 2 `.pc` files |
| `/usr/local/share/gtk-doc/html/libvips` | 49 | API reference HTML; 6 `*.md.html` pages renamed to `*.html` |
| `/var/cache/ldconfig/aux-cache` | 1 | ldconfig cache |

Most header changes are unrelated to the untrusted flag. For example,
`arithmetic.h` gains `VIPS_API` export markers and includes. The diff
contains the whole release, not just eba9ec0.

## What shows up for the untrusted flag

Only primary evidence from the two built images is recorded here.

**1. Library API.** `nm -D --defined-only libvips.so.42`:

| Symbol | 8.12.2 | 8.13.0 |
| --- | --- | --- |
| `vips_block_untrusted_set` | absent | **present** |
| `vips_operation_block_set` | absent | **present** |

`strings` on the 8.13.0 library also shows `VIPS_BLOCK_UNTRUSTED`,
`VIPS_OPERATION_UNTRUSTED` and `, untrusted`. None of these strings is in
8.12.2.

**2. Operation flags in `vips -l`.** The full listings are
`cit-272/vips-l-8.12.2.txt` (359 lines) and `vips-l-8.13.0.txt` (361 lines).

- In 8.13.0, **42 operations** carry an `untrusted` flag. In 8.12.2 none do,
  because the flag doesn't exist there.
- 39 of the 42 are loaders or loader base classes:
  - `csvload*`, `rawload`, `vipsload*`, `analyzeload`, `ppmload*`
  - `radload*`, `pdfload*` (poppler), `svgload*` (rsvg), `jp2kload*`
  - `matload`, `openslideload*`, `magickload*`, `fitsload*`, `openexrload`
- The other 3 are savers: `magicksave*` and `fitssave`.
- The JPEG, PNG, WebP, TIFF, GIF and HEIF loaders are **not** marked.
- `magickload*` is marked, so libvips' own ImageMagick bridge is untrusted
  as well. The commit message says: "although \*magick is fuzzed, it's
  probably safer to disable it in untrusted environments".

**3. The switch works, at the CLI.** Two inputs were loaded with and without
`VIPS_BLOCK_UNTRUSTED=1`: a 2×2 CSV through `csvload`, and a BMP made with
ImageMagick's `convert` and loaded through `magickload`.

| | 8.12.2 | 8.13.0 |
| --- | --- | --- |
| env unset | both load | both load |
| `VIPS_BLOCK_UNTRUSTED=1` | both load (the variable means nothing to 8.12.2) | `csvload: operation is blocked`, `magickload: operation is blocked` |

So the default is **off** in 8.13.0 too: untrusted loaders run unless the
host process opts in. No malicious input was used; canary and file-read
tests are CIT-278's job.

**4. ruby-vips binding.** The same `ruby-vips` 2.3.0 is installed in both
images.

- In 8.13.0, `Vips.respond_to?(:block_untrusted)` is `true` and
  `Vips.block_untrusted(true)` succeeds.
- In 8.12.2, it is `false`, and calling it raises
  `NoMethodError: undefined method 'block_untrusted'`.

The binding defines the method only when the loaded libvips reports version
8.13 or later (`if at_least_libvips?(8, 13)`, `ruby-vips-2.3.0/lib/vips.rb:827-835`). This is the first place in
the stack where the new control is reachable from Ruby.

**5. Where the component "says never" inside the deployed image.** With a
default install, `grep -rIli untrusted` over `/usr/local/include/vips`,
`/usr/local/share` and `/usr/local/bin` finds six files in 8.13.0 and none in
8.12.2:

| File | Hits | Content |
| --- | --- | --- |
| `include/vips/operation.h` | 1 | `VIPS_OPERATION_UNTRUSTED = 16` in `VipsOperationFlags` |
| `include/vips/vips.h` | 1 | `void vips_block_untrusted_set( gboolean state );` |
| `share/gtk-doc/html/libvips/VipsOperation.html` | 6 | flag documentation (quoted below) |
| `share/gtk-doc/html/libvips/libvips-vips.html` | 9 | `vips_block_untrusted_set()` docs, incl. the env var |
| `share/gtk-doc/html/libvips/api-index-full.html` | 1 | index entry |
| `share/gtk-doc/html/libvips/libvips.devhelp2` | 2 | index entry |

The operative sentence, from `VipsOperation.html`:

> `VIPS_OPERATION_UNTRUSTED` means the operation depends on external
> libraries which have not been hardened against attack. It should probably
> not be used on untrusted input. Use vips_block_untrusted_set() to block
> all untrusted operations.

Note the wording for hint level 1: this is **"should probably not"**, not
"must never", and it sits in generated API HTML and a header enum, not in a
runtime warning. The commit history shows a startup warning was drafted and
then removed before merge ("remove the annoying 'untrusted' warning message
/ better to warn on the download page"). A download-page warning isn't
installed anywhere in the image. `ChangeLog`/`NEWS` stay in the build tree
and are not installed by `make install`.

**The binding carries the same mention on both sides.** The grep above only
covers libvips' own install paths. Running `grep -rIli untrusted
/usr/local/bundle/gems` in the **8.12.2** image turns up two ruby-vips 2.3.0
files, both in the shared layer:
- `ruby-vips-2.3.0/CHANGELOG.md:34`: "add `Vips.block_untrusted` method to
  block all untrusted operations. Only for libvips >= 8.13."
- the `block_untrusted` comments in `lib/vips.rb:831-832`.

The other hits are unrelated uses of the word, in nokogiri, net-imap,
activerecord, logger, timeout and rails-html-sanitizer.

So the gem-level breadcrumb isn't part of this diff. Both images have it,
and so do CIT-277's `after` image and CIT-281's `:mini_magick` control,
since all of them use the same ruby-vips 2.3.0. It isn't a signal that
separates the positive state from the matched control. Only the libvips
paths in table 5 differ.

**6. Consumer side, same image.** `grep -rniE
"untrusted|block_untrusted|operation_block"` over the installed
`activestorage-7.0.10` and `image_processing-1.14.0` gems finds **zero**
matches. In this image the control exists in libvips and is exposed by
ruby-vips, but neither Active Storage nor image_processing calls it. That is
edge E6 from the CIT-280 review, checked by grep for these two gem versions
only. It doesn't show that uploads reach an untrusted loader (E2–E4, which
is CIT-278).

## For CIT-278, CIT-281 and CIT-271

- **CIT-278:** `libvips-cit272:8.13.0` is the image it asks for: libvips
  8.13.0, ruby-vips 2.3.0 (≥ 2.2.1), unpatched Active Storage 7.0.10,
  ImageMagick installed. Run `bin/rails db:prepare` first. Arm B's switch is
  shown to work at the CLI above.
- **CIT-281 / CIT-271 level-0 state:** the package-level item from this diff
  is just `libvips 8.12.2 → 8.13.0`. The file-level diff is almost entirely
  libvips paths, so it needs no noise filtering. Whether the six files in
  table 5 go into `files` is a CIT-281 decision. Including them hands over
  the "should probably not" sentence. Leaving them out means level 0
  contains only a version bump.
- **Caveat on realism:** these libvips builds are from source into
  `/usr/local`, not a distro package upgrade. A distro upgrade (e.g. Debian
  bullseye 8.10.5 → bookworm 8.14.x) would bury this change under an
  OS-wide diff. The fixture isolates the change on purpose, and that makes
  detection easier than a real deployment would.
