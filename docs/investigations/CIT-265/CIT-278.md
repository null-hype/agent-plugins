# CIT-278: canary control, untrusted loader with and without blocking

Runs the cheapest control from the [CIT-280 review](../CIT-265.md) (section 3
of that comment): upload a harmless canary that makes an untrusted image
loader *try to read a known dummy file*, and record whether it's read under
each arm. This tests edges **E2–E4** (does an upload actually reach an
untrusted loader, and does that loader read a local file) and whether the
libvips block switch (**E5**) stops it, using the [CIT-272](./CIT-272.md)
after image. Everything referenced lives under [`cit-278/`](./cit-278).

## Images

  `FROM libvips-cit272:8.13.0` (build CIT-272 first). libvips **8.13.0**,

  ImageMagick 6.9.11 installed. Adds `strace`, runs `bin/rails db:prepare`

  (apt). For the "Rails 6.1 with `:vips` set explicitly" arm.

## Loaders (`vips -l`)

`vips -l` in the after image lists **42 operations flagged `untrusted`**
([`cit-278/vips-l-8.13.0.txt`](./cit-278/vips-l-8.13.0.txt)) — the same set
CIT-272 recorded (39 loaders/base classes incl. `svgload`, plus `magicksave*`
and `fitssave`). JPEG/PNG/WebP/TIFF/GIF/HEIF are not flagged. The canary
below drives **`svgload`**, one of the flagged loaders.

## Canary and detection

The canary is an SVG whose `<image xlink:href="...">` points at a dummy text
file (`CANARY-…`, not a secret). When the loader *renders* the SVG it tries
to load the referenced resource, which opens the file. Detection is external:
`strace -f -e trace=openat -y` on the `bin/rails runner`, grepping for an
`O_RDONLY` open of a canary path. Raw per-arm evidence:
[`cit-278/canary-reads.txt`](./cit-278/canary-reads.txt).

**Where the loader is reached.** Active Storage runs its image *analyzer* on
every upload, but the analyzer only reads the SVG header for dimensions and
does **not** fetch external references. The read happens on *variant
processing* (a real render): `blob.variant(...).processed` downloads the blob
to a temp file in `/tmp` and hands it to `image_processing`, which calls the
configured backend. So the runner
([`cit-278/canary_runner.rb`](./cit-278/canary_runner.rb)) requests a variant.

**Content-type gate (a finding, not in the issue).** Passing
`content_type: "image/png"` on the upload does **not** get an SVG past the
variant allowlist: `ActiveStorage::Blob.create_and_upload!` re-identifies the
type from the bytes via Marcel and stores `image/svg+xml`, which is not a
default `variable` type. So the naive "declare a variable type, send other
bytes" mismatch is caught by stock Active Storage unless the app disables
`identify` or a polyglot fools Marcel *and* libvips into different types.
This experiment instead uses the realistic precondition above (the app
thumbnails SVGs).

## Arms

Canary SVG references a **same-directory** dummy (relative + absolute in
`/tmp`, where Active Storage writes the temp SVG) for A/B/C/6.1, and a
**cross-directory** absolute dummy (`/work`) for the A′/C′ pair.

| Arm | Processor | libvips | Env | Dummy read? |
| --- | --- | --- | --- | --- |
| **A** | `:vips` | 8.13.0 | — | **read** (`svgload` opens the `/tmp` dummy) |
| **B** | `:vips` | 8.13.0 | `VIPS_BLOCK_UNTRUSTED=1` | **not read** — `Vips::Error: svgload: operation is blocked` |
| **C** | `:mini_magick` | 8.13.0 | — | see below (ImageMagick, reference-form dependent) |
| **6.1** | `:vips` (explicit) | 8.10.5 | — | **read** |
| **6.1** | `:vips` (explicit) | 8.10.5 | `VIPS_BLOCK_UNTRUSTED=1` | **read** — the env var is a **no-op** on 8.10.5 |

- **A vs B** is the headline: the same upload that reaches `svgload` and reads
  a local file with blocking off is refused outright with
  `VIPS_BLOCK_UNTRUSTED=1`. The variant still "succeeds" in A (it renders a
  blank box where the unreadable dummy would go) — the read is the effect,
  not a crash.
- **6.1 arm** reproduces A on Rails 6.1.7 with `variant_processor` set
  explicitly to `:vips`: the exposure exists wherever `:vips` is selected, not
  only after the Rails 7 default flip. And `VIPS_BLOCK_UNTRUSTED=1` does
  nothing on libvips 8.10.5 — matching the advisory's "earlier versions
  (< 8.13) cannot disable unfuzzed operations at all."

### The two loaders follow references by different rules

No single reference form makes both backends read, because their base-path
policies differ. This is itself the result, so it's given as a matrix rather
than hidden behind one canary:

| Reference in the SVG | `:vips` (librsvg 2.50) | `:mini_magick` (ImageMagick 6.9) |
| --- | --- | --- |
| relative sibling (`canary.txt`) | **read** (resolved against the SVG's dir) | not read — resolved against the process CWD (`/app`), `ENOENT` |
| absolute, same dir as SVG (`file:///tmp/…`) | **read** | not followed here |
| absolute, other dir (`file:///work/…`) | **not read** — librsvg refuses cross-directory | **read** (follows absolute `file://`) |

So arm **C** does read a local file, but only via a reference form
ImageMagick follows (absolute, arm C′ in the evidence: two `O_RDONLY` opens
of `/work/canary_xdir.txt`); with the same-directory canary A/B use, IM's
relative attempt misses in `/app`.

## What this shows, against the review's edges

- **E2–E4 (demonstrated for the `:vips` path):** an untrusted upload
  processed as an Active Storage variant does reach an untrusted libvips
  loader (`svgload`), which reads a local file. Previously advisory-only.
- **E5 (demonstrated):** `VIPS_BLOCK_UNTRUSTED=1` blocks that loader on
  8.13.0, and is inert on 8.10.5 — the switch is what the advisory says
  Active Storage's fix relies on, and it only exists from 8.13.
- **Arm C partially fires the falsifier.** The review said: if `:mini_magick`
  reads the dummy too, the file-read is a generic "native parser on untrusted
  uploads" problem (ImageTragick class), not a libvips/Rails-specific
  composition. It does read (via absolute references). So the *file-read
  primitive* is not unique to libvips; what is libvips-specific is the
  **ability to turn it off** (`VIPS_BLOCK_UNTRUSTED`), which ImageMagick's
  policy files address differently and which the Rails default flip changed
  the exposure to.
- **6.1 arm:** the Rails 7.0 `variant_processor` flip is an **exposure
  multiplier**, not the cause — `:vips` on 6.1 reads the same way.

## Impact caveat (bears on the advisory's "read the process environment")

For the **`:vips`** path in this image, librsvg only follows references
inside the SVG's own directory. Active Storage renders from a random temp file
in `/tmp`, whose siblings an attacker does not control, and cross-directory
references (`/work`, `/proc/self/environ`) are refused. So `svgload` here is a
**directory-confined** read, not the arbitrary read the advisory describes.
The unrestricted arbitrary-file read (including absolute paths like the
process environment) reproduced via **`:mini_magick`/ImageMagick**, which
follows absolute `file://` references. Reproducing arbitrary read through the
*libvips* untrusted loaders specifically would need a different loader or a
librsvg built/loaded with external-resource limits relaxed — not shown here.
This is the honest limit of what the SVG/`svgload` canary demonstrates.

## For CIT-282

- The composition claim "an untrusted upload reaches an untrusted loader and
  the consumer never used the available off switch" is now demonstrated for
  the `:vips` path (E2–E5), where before it was advisory-only.
- The weakest remaining edge is *impact*: the `:vips` read shown here is
  directory-confined, so "arbitrary file read / environment disclosure" is
  demonstrated only via `:mini_magick`. Whether the real CVE's libvips read
  primitive is `svgload`+librsvg or a different untrusted loader is unresolved
  and is the natural next probe.
