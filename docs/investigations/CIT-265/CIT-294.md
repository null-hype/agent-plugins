# CIT-294: live MATLAB/HDF5 file-read path and blocking controls

Runs the remaining proof [CIT-265](../CIT-265.md) asked for: a live
**Rails → libvips `matload` → libmatio/HDF5 → dummy file bytes → returned
variant** chain, not the synthesized-PNG-variant forensics fixture
([`test/_global/cve-2026-66066-forensics/make_fixture.py`](../../../test/_global/cve-2026-66066-forensics/make_fixture.py))
that proves *recognition* of evidence but not that the MATLAB path actually
produces it. Reuses [CIT-278](./CIT-278.md)'s canary methodology (upload a
canary that makes an untrusted loader try to read a known dummy file; detect
the read externally with `strace`; compare with and without
`VIPS_BLOCK_UNTRUSTED`) and the same Rails 7.0.10 app lineage
([CIT-277](./CIT-277.md)'s `after`), applied to `matload` instead of
`svgload`. Everything referenced lives under [`cit-294/`](./cit-294).

The pinned reference for the mechanism being reproduced is
[`src/cve-2026-66066/vendor/reference/the-attack.md`](../../../src/cve-2026-66066/vendor/reference/the-attack.md).

## Why bookworm, not bullseye

CIT-272/277/278 all build on `ruby:3.0-bullseye`. CIT-294 instead builds on
`ruby:3.1-bookworm` (Gemfile's `ruby '3.0.7'` pin dropped, nothing else
changed — no Ruby 3.0.x bookworm image is published, and nothing in the
CVE's mechanism depends on the interpreter's minor version). This is a
deliberate, evidenced deviation, not drift, and it took four isolation
builds in a scratch environment to pin down:

| # | Base | libmatio | HDF5 | HDF5 **external-storage** dataset via `vips copy` | same dataset **inline** |
|---|---|---|---|---|---|
| 1 | bullseye | 1.5.19 (apt) | 1.10.6+repack-4+deb11u1 | **fails**: `mat2vips: unsupported class type 0` | — |
| 2 | bullseye | 1.5.19 (apt) | 1.10.6+repack-4+deb11u1 | — | **succeeds**, byte-exact |
| 3 | bullseye | 1.5.23 (built from source against bullseye's HDF5) | 1.10.6+repack-4+deb11u1 | **fails**, same error | — |
| 4 | bookworm | 1.5.23 (apt) | 1.10.8+repack1-1 | **succeeds**, byte-exact | — |

Row 1 vs. 2 isolates the failure to HDF5 **external** storage specifically
(same attribute/structure, same libmatio, only the storage mechanism
differs) — not a flaw in the crafted file's `MATLAB_class` attribute or
header. Row 1 vs. 3 rules out the libmatio version itself: rebuilding
libmatio 1.5.23 from source *against bullseye's own HDF5 1.10.6* reproduces
the exact same failure, so upgrading libmatio alone doesn't fix it. Row 3
vs. 4 — the only remaining difference is the HDF5 library version (plus,
not independently re-tested, any build-flag difference between Debian's
bookworm package and this from-source build) — is where it starts working.

Mechanically: `libvips`' `matload` calls libmatio's generic
`Mat_VarReadNextInfo`, which on bullseye's HDF5 returns a matvar with
`class_type == 0` (`MAT_C_EMPTY`) for an externally-stored dataset, which
`mat2vips_get_header` in `libvips/foreign/matlab.c` then rejects as
unsupported. `matdump` (libmatio's own CLI, used throughout this
investigation to sanity-check crafted files before touching Rails) does
**not** hit this: its `-d`/`-f whos` path does a full `Mat_VarReadDataAll`,
not the info-only probe libvips' `mat2vips.c` calls first — so a file that
`matdump -d -f whos` reads perfectly can still fail through libvips alone.
This is itself worth recording: a tool-based sanity check of a crafted HDF5
file is not the same claim as "the actual loader this CVE routes through
can read it."

## The canary: a MATLAB 5.0/7.3 dual identity, for real

[`cit-294/craft_mat_canary.py`](./cit-294/craft_mat_canary.py) builds the
canary file empirically verified against a libmatio-written reference (see
its own module docstring for the exact byte-level reasoning), not assumed
from the advisory text alone:

1. Wrote a genuine MAT 7.3 file with libmatio's own C API
   (`Mat_CreateVer`/`Mat_VarCreate`/`Mat_VarWrite`) and diffed it byte-for-
   byte to learn the real on-disk shape: a 512-byte userblock, one root HDF5
   dataset per variable, a `MATLAB_class` attribute that must be a
   **fixed-length, `NULLTERM`-padded** ASCII string — h5py's high-level
   string-attribute API defaults to variable-length/`NULLPAD`, which
   libmatio's reader silently reads back as `class_type 0`/empty, not an
   error. Getting this one attribute's exact HDF5 type wrong is a second,
   independent way to reach the same "unsupported class type 0" failure the
   bullseye/bookworm HDF5 difference above also produces — the module
   docstring and inline comments in `craft_mat_canary.py` record the fix
   (`h5a.create` with an explicit matching `mtype`, not the array's own
   default memory type, which otherwise reserves the attribute's last byte
   for a null terminator and truncates `"uint8"` to `"uint"`).
2. Gave the dataset HDF5 **External File List** storage
   (`h5py`'s `external=[(path, offset, length)]`) pointing at a test-owned
   dummy file — this, not the attribute, is the actual file-read primitive
   `the-attack.md` describes.
3. Overwrote only the first 10 bytes of the 128-byte header to claim
   `"MATLAB 5.0"` while leaving the version field at bytes 124–125 honest
   (`0x0200`, MAT 7.3) — the same "structurally genuine 7.3 container,
   spoofed descriptive text" construction `the-attack.md`'s "Why the file
   must be structurally inconsistent" section documents, built here rather
   than assumed.

Confirmed directly against real libvips/libmatio (not just matdump) before
ever touching Rails: `VIPS_BLOCK_UNTRUSTED=1 vips copy canary.mat out.v`
raises `matload: operation is blocked`; without it, `vips copy` succeeds
with `vips-loader: matload` and the output's raw pixels are the dummy
file's bytes exactly.

## The Rails upload path: declared content type, uninspected bytes

`the-attack.md`'s Junction 1 is that a **direct upload**
(`ActiveStorage::Blob.create_before_direct_upload!`) persists the
client-declared `content_type` without ever calling
`identify_without_saving` — unlike a server-side attach, which sniffs the
bytes with Marcel. [`cit-294/canary_runner.rb`](./cit-294/canary_runner.rb)
reproduces this exact effect in one process with
`ActiveStorage::Blob.create_and_upload!(content_type: "image/png", identify:
false)`, which activestorage's own `blob.rb` documents as the way to get
this precise effect ("When providing a content type, pass `identify: false`
to bypass automatic content type inference") rather than driving two real
HTTP requests to simulate it. Confirmed from the blob's own state after
upload: `stored_content_type` comes back `"image/png"` for the MAT canary
in every run — the declared type, retained, despite the real bytes being
the MAT/HDF5 payload. (`identified` is `true` regardless, in both the MAT
and PNG arms — `Blob#unfurl` sets that flag unconditionally; it means
"checksum/byte_size were computed," not "Marcel verified the type," and
isn't the signal to read here. `stored_content_type ==
declared_content_type` is.)

Unlike CIT-278's SVG canary, no `variable_content_types` initializer patch
is needed: `image/png` is already a default Active Storage variable type,
so uploading MAT bytes *declared* as PNG exercises
`representable.rb`'s `variable?` check (Junction 1) directly.

The variant transformation is `resize_to_limit: [64, 64, { sharpen: false
}]`. `sharpen: false` is the one deliberate deviation from CIT-278's
`resize_to_limit: [48, 48]`: `image_processing`'s `Vips::Processor#thumbnail`
applies a sharpening convolution (`image.conv(sharpen, ...)`) after every
resize by default, which mixes neighbouring pixel values even when the
resize itself is a no-op (the canary's image is 1×16, already smaller than
the 64×64 limit) — found empirically, by getting `matches_dummy_file:
false` on the first real run despite every other signal (loader, variant
success) being correct, then reading
`image_processing-1.14.0/lib/image_processing/vips.rb` to find the
convolution. Disabling it has no bearing on the vulnerability: it runs
after libvips/libmatio have already loaded the file and resolved the
external reference, and this is checking that the resolved bytes reach the
response unaltered, not re-deriving whether they're reachable.

## Arms and results

One pinned configuration (recorded live from the built image, not
transcribed by hand: [`cit-294/versions.txt`](./cit-294/versions.txt) —
Ruby 3.1.7, Rails 7.0.10, Active Storage 7.0.10, ruby-vips 2.3.0, libvips
8.13.0, libmatio 1.5.23, HDF5 1.10.8), four runs (the PNG control runs under
both blocking states, per scope). Each run is `bin/rails runner
canary_runner.rb` under `strace -f -e trace=openat`, env-gated by
`CIT294_INPUT` (`mat`/`png`) and `VIPS_BLOCK_UNTRUSTED`. Raw transcripts:
[`cit-294/canary-reads.txt`](./cit-294/canary-reads.txt); structured
per-arm JSON: [`cit-294/observations/`](./cit-294/observations).

| Arm | `VIPS_BLOCK_UNTRUSTED` | Loader selected | Variant | Dummy file opened (independent `strace`) | Bytes recovered |
| --- | --- | --- | --- | --- | --- |
| MAT canary | unset | `matload` | succeeds | **yes** — one `openat` from the libvips worker thread, no `O_CLOEXEC` (distinct from the script's own file handling) | **yes**, byte-exact: `KR2S-CANARY-CIT294-0123456789abc` |
| MAT canary | `1` | *(none — refused before selection completes)* | `Vips::Error: matload: operation is blocked` | **no** | — |
| PNG control | unset | `pngload` | succeeds | n/a | ordinary 2×2 black PNG, unchanged |
| PNG control | `1` | `pngload` | succeeds | n/a | unchanged — blocking a 42-loader untrusted set doesn't touch `pngload` |

The canary_runner.rb script hardcodes the dummy file's expected bytes as a
literal rather than reading `/work/dummy-canary.txt` itself — otherwise the
script's own read would be indistinguishable in the `strace` trace from the
read being measured. The evidence above is that **only** the libvips
worker thread opens that file, and only in the unblocked arm. Per CIT-297
below, this is no longer only a prose claim about the transcript: the
"independent `strace`" column is itself a Pkl-checked field
(`independent_dummy_file_openat_count`), bound to each arm's verdict rather
than left for a human to eyeball.

## Declared/observed/checked: the Pkl records

Per CIT-265's requirement to relate input, configuration, blocking state,
loader selection, the independent file-read observation and returned bytes
through case-owned Pkl records — not ad hoc prose — the same
declared/observed/checked split `src/noteexpand` established is applied
here, scoped to these four runs (no installed feature; this is case-owned
investigation evidence, same as the merged forensics fixture's own
`claim.json`/`observation.json`/`diagnostics.json` triple):

- [`cit-294/Observation.pkl`](./cit-294/Observation.pkl) — the typed shape
  of each arm's combined record. Fields without an `independent_` prefix
  are `canary_runner.rb`'s own self-report (its JSON stdout) — nothing
  declared or expected, just what the live Rails/libvips process said
  happened. `independent_*` fields are computed entirely outside that
  process by `run_arms.sh` — parsed from the `strace` transcript of the
  same invocation, plus `docker image inspect`/`sha256sum` against the
  pinned image afterward (dummy-file open count, source byte identity,
  image identity, and the live `load_defaults`/`variant_processor`
  configuration) — so a tampered or missing self-report cannot also
  fabricate the independent half. (Added in response to CIT-297: this
  evidence previously existed only as grepped text in canary-reads.txt,
  which Pkl never consumed — deleting it, or forging a dummy-file read into
  the blocked arm's trace, still passed the full suite.)
- [`cit-294/Claims.pkl`](./cit-294/Claims.pkl) — the four declared
  expectations, written against `the-attack.md` and
  `VIPS_BLOCK_UNTRUSTED`'s documented behaviour, independently of the
  observations: loader, content-type retention, variant outcome,
  whether the independent trace must show the dummy file opened, the
  *specific* exception class/message a blocked arm's variant call must
  raise (not merely that something failed), and the exact expected byte
  count and hex-encoded bytes the returned variant must equal.
- [`cit-294/Reconcile.pkl`](./cit-294/Reconcile.pkl) — `check(claim,
  observed)`, flagging any disagreement between the two. Checks the
  *actual variant's* `variant_error_class`/`variant_error` against the
  claimed refusal (not the preliminary loader-probe's `loader_error` —
  a generic crash no longer passes as a successful block); validates
  `returned_bytes_hex`/`returned_byte_count` directly against pinned
  expected values rather than trusting `matches_dummy_file` alone, and
  separately flags disagreement between that raw data and the boolean
  describing it; and flags disagreement between `independentReadExpected`
  and the independently-observed `independent_dummy_file_openat_count`.
- [`cit-294/diagnose.pkl`](./cit-294/diagnose.pkl) — this case's actual
  "detector output": `Reconcile.check`'s flags for each arm, run against
  the real `observations/*.json` and written to
  [`cit-294/reports/diagnostics.json`](./cit-294/reports/diagnostics.json)
  by `run_arms.sh` (`pkl eval -f json diagnose.pkl -o
  reports/diagnostics.json`). An empty list per arm in that committed file
  is itself the evidence that Reconcile found no disagreement — the
  noteexpand pattern's `diagnostics.json`, produced by a real
  `noteexpand-detect` invocation, is what this follows; CIT-294 has no
  installed detector binary, so this module *is* the detector invocation.
- [`cit-294/cit294.test.pkl`](./cit-294/cit294.test.pkl) — `pkl:test` facts
  over the real `observations/*.json`, including eight negative-control
  facts (deliberately wrong claims, generic crashes, emptied/corrupted
  bytes, and a deleted or falsified independent trace all get flagged, so
  the checker isn't vacuously green — see CIT-297), and a committed
  [`cit294.test.pkl-expected.pcf`](./cit-294/cit294.test.pkl-expected.pcf)
  golden. `run_arms.sh` runs `pkl test --junit-reports reports
  cit294.test.pkl`, committing the real JUnit result to
  [`cit-294/reports/cit294.test.xml`](./cit-294/reports/cit294.test.xml) as
  the authoritative check result — not just a pass/fail count narrated in
  this write-up: 18 facts / 56 asserts / 4 examples, all passing against the
  live data.

### Strengthened per CIT-297 review

[CIT-297](https://linear.app/citizen6librarian6refrain4/issue/CIT-297/request-changes-to-strengthen-cit-294-evidence-validation)
reviewed the commit this section originally described and found the
checker could certify contradictory or incomplete evidence despite a
green 8-facts/28-asserts suite: deleting the strace trace, or forging a
dummy-file read into the blocked arm, still passed; a generic crash
(`RuntimeError: disk full`) still passed as a successful block; and
emptying the returned pixels or corrupting the PNG control's pixels while
leaving `matches_dummy_file` untouched still passed. Verified by
reproducing each of those five mutations against the live
`observations/*.json` (not inline Pkl literals) and confirming each one now
fails `pkl test` as expected, plus two additional direct-`Reconcile.check`
attacks the review named (a crash with no error info at all; an unblocked
observation with every returned-byte field stripped but the boolean left
`true`) — both now flagged. The fixes above (`independent_*` fields,
variant-error-specific checks, raw byte/hex validation, and the
`diagnose.pkl`/`reports/` hookup) are the result.

## What this demonstrates, and labeling live vs. recorded

- **The MATLAB path actually produces the bytes.** The forensics fixture
  ([CIT-291](https://linear.app/citizen6librarian6refrain4/issue/CIT-291/create-devcontainer-testing-skill-and-refactor-method-tests),
  merged in #115) synthesizes its "rendered variant" PNGs in
  `make_fixture.py` and never calls libvips or libmatio at all — it proves
  recognition of stored evidence. This run is the first time in this
  project's CIT-265 work that `libvips`'s real `matload` loader and the
  real system `libmatio`/HDF5 stack actually execute the MAT 7.3 External
  File List read and hand real bytes back through a real Active Storage
  variant. Anything described above as "recorded" (the pinned versions
  table, the committed `canary-reads.txt`/`observations/*.json`) is a
  transcript of that one live execution, not a hand-authored stand-in for
  it — rerunning `docker build` + the four
  `docker run` invocations in
  [`cit-294/Dockerfile`](./cit-294/Dockerfile)'s header comment, or just
  `./run_arms.sh` against the already-built `cit294:live` image, reproduces
  it from scratch. The actual detector output
  ([`reports/diagnostics.json`](./cit-294/reports/diagnostics.json)) and
  authoritative check result
  ([`reports/cit294.test.xml`](./cit-294/reports/cit294.test.xml)) that
  `run_arms.sh` produces and this write-up links are retained artifacts of
  that same execution, not prose summarizing it.
- **Blocking is a real, observable refusal, not a crash.** The blocked
  arm's *actual variant call* raises a specific `Vips::Error` naming the
  blocked operation (`matload: operation is blocked`) — checked directly
  against `variant_error_class`/`variant_error`, not the preliminary
  loader-probe's `loader_error` — the independent `strace` evidence
  (`independent_dummy_file_openat_count == 0`, computed outside the Ruby
  process) confirms the dummy file is never opened, and the PNG control
  confirms the refusal is scoped to the untrusted-loader set rather than
  breaking image processing generally. `Reconcile.pkl` enforces all three
  together, and `cit294.test.pkl`'s negative controls confirm a generic
  crash (e.g. a stand-in `RuntimeError`) is flagged rather than accepted —
  closing this issue's explicit "a generic crash alone is insufficient"
  condition structurally, not just by narration (see CIT-297 above).
- **Content-type retention is the actual precondition, demonstrated, not
  asserted.** `stored_content_type` is observed directly from the blob
  after upload, in both the disclosure and refusal arms.
- **Byte recovery is validated, not trusted through a boolean.** Each
  arm's `returned_bytes_hex`/`returned_byte_count` are checked directly
  against the pinned expected values in `Claims.pkl`, and cross-checked for
  internal consistency against the self-reported `matches_dummy_file`
  boolean — not accepted on that boolean alone (see CIT-297 above).

## Limits

- **Directory-confined vs. arbitrary read**, same caveat CIT-278 recorded
  for `svgload`: this canary's External File List entry names a test-owned
  dummy file in `/work`, not an arbitrary path like
  `/rails/config/master.key`. Nothing about the HDF5/matio mechanism
  constrains the path an External File List entry can name (unlike
  `svgload`'s librsvg, which refuses cross-directory references) — the
  forensics fixture's own target, `/rails/config/master.key`, is a plain
  path string in the same structure this canary uses — but this
  investigation's canary deliberately avoids pointing at anything
  sensitive, matching CIT-278's and the vendored forensics repo's own rule
  against shipping a retargetable exploit generator. Confirming the HDF5
  path field in this file format is unconstrained is a documentation
  reading of `the-attack.md`, not independently re-derived here.
- **bullseye vs. bookworm isolation is to the HDF5 version, with one
  residual confound.** The four-row matrix above isolates the failure away
  from the crafted file's structure and away from the libmatio version
  alone. It does not independently rule out a libmatio *build-flag*
  difference between Debian bookworm's package and the from-source 1.5.23
  build in row 3 (e.g. an HDF5-related `./configure` flag Debian's
  packaging passes that a bare `./configure` does not) as a contributing
  factor alongside the HDF5 version itself.
- **Blind discovery and Jev calibration are explicitly out of scope here**,
  per this issue's own text — this reproduces the path under a hint-ladder
  level-3 (ceiling check) configuration; whether a free agent or Jev finds
  this composition unprompted is
  [CIT-275](https://linear.app/citizen6librarian6refrain4/issue/CIT-275/run-the-jev-fixture-and-negative-control)/[CIT-288](https://linear.app/citizen6librarian6refrain4/issue/CIT-288/experiment-dagger-module-applying-the-method-to-a-case)'s
  question, not this one's.
