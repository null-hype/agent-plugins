# CIT-277: snapshot diff, in-place Rails upgrade on an app that already processes images

Complement to [CIT-270](./CIT-270.md). CIT-270 isolated the bare Rails-version
bump on two *independent* fresh `rails new` apps and found that neither
version installs `image_processing`/libvips/ImageMagick by default, so the
`variant_processor` default flip left no application-level trace. This
fixture instead builds **one app lineage** that already has
`image_processing` + `mini_magick` + `ruby-vips` wired up and ImageMagick +
libvips both installed at Rails 6.1.7 (`before`), then performs a genuine
**in-place upgrade** to 7.0.0 (`after`, `FROM before`) -- Gemfile rails
constraint bump, `bundle update`, `config.load_defaults` flip, and an actual
`bin/rails app:update` run -- and restic-diffs the two resulting containers.
Everything referenced lives under [`cit-277/`](./cit-277).

## Build

`cit-277/Dockerfile`, multi-stage: `base` (Ruby 3.0-bullseye + apt packages,
including `imagemagick` and `libvips-tools`/`libvips-dev` this time, unlike
CIT-270) -> `before` (Rails 6.1.7, `rails new`, then `image_processing`,
`mini_magick`, and `ruby-vips` added to the Gemfile so both installed native
libraries are actually exercised, not just present) -> `after` (`FROM
before`: bump the Gemfile's `gem 'rails'` line to `~> 7.0.0`, `bundle update`
with `jobs=1`, flip `config.load_defaults 6.1` to `7.0`, then `yes a | bin/rails
app:update`).

```
docker build --target before -t rails-cit277:before .
docker build --target after -t rails-cit277:after .
```

One thing worth recording plainly: a scoped `bundle update rails
--conservative` was tried first and abandoned. Every default Gemfile
dev/asset gem (`web-console`, `sass-rails`, etc.) transitively depends on
`railties`, so a conservative update just turns into re-pinning each of them
one at a time rather than actually resolving the upgrade -- a full `bundle
update` is what a real developer doing this upgrade would end up running
too, not a scoping mistake on this fixture's part. On this environment (2
CPU, 7.8GB RAM, no swap), that full resolve took **~41 minutes** of
wall-clock time for the `after` build (`bundle update` was the only slow
step; everything else was cache-hit from `before`) -- worth noting as a
resource-constraint data point for anyone re-running this, not a defect in
the method.

Generated app trees (stripped of `tmp/`, `log/`, `storage/`, `*.sqlite3`) are
committed at [`generated-apps/before/`](./cit-277/generated-apps/before) and
[`generated-apps/after/`](./cit-277/generated-apps/after).

## Diff method

Same technique as CIT-270: each image's full container filesystem exported
(`docker create` + `docker export | tar -x --numeric-owner`) and backed up
into a disposable local restic repo under the same literal path for both
snapshots (restic diffs by tree position). Confirmed as a real content diff,
not pure add/remove: the second backup reported `2,631 new, 33,997 changed`
against the first, not `0 changed`.

Full raw output, path-normalized:
[`restic-diff-before-to-after.txt`](./cit-277/restic-diff-before-to-after.txt)
(3,162 lines -- far smaller than CIT-270's 13,489, because this diff is a
true in-place upgrade of one lineage rather than two independently generated
apps, so there's no gem-duplication noise and no unrelated Webpacker/JS
churn to wade through). Headline stats: `Files: 2,631 new, 0 removed, 25
changed`; `Added: 31.0 MiB`, `Removed: 15.2 MiB`. The 25 *changed* (not
new/removed) files are the actual in-place-modified application files --
`config/application.rb` and several `config/initializers/*.rb` generator
templates among them -- everything else is new/old Rails gem versions
replacing each other wholesale.

## What actually shows up for libvips and ImageMagick

**Unchanged at both stages, by design and confirmed identical:**

```
image_processing (1.14.0)
  mini_magick (>= 4.9.5, < 6)
  ruby-vips (>= 2.0.17, < 3)
mini_magick (4.13.2)
ruby-vips (2.3.0)
```

Confirmed live in both running containers: `ImageMagick 6.9.11-60 Q16` and
`vips-8.10.5` -- identical native library versions on both sides. None of
this is what the Rails upgrade touches; it's the fixed backdrop that makes
the variant_processor question meaningful here, unlike CIT-270 where nothing
was installed to have an opinion.

## What actually shows up for Active Storage / variant_processor

This is the fixture's actual payload, and it's now checkable **live**, not
just in gem source. Ran `bin/rails runner 'puts
Rails.application.config.active_storage.variant_processor.inspect'` against
each built image directly:

| Stage | Effective `variant_processor` | Resolves to |
| --- | --- | --- |
| `before` (Rails 6.1.7.10) | `nil` | `:mini_magick` (framework fallback, per `activestorage`'s `mattr_accessor` default) |
| `after` (Rails 7.0.10) | `:vips` | `:vips` |

Same mechanism CIT-270 traced through gem source (`load_defaults`'s `when
"7.0"` branch setting `active_storage.variant_processor = :vips`), now
confirmed as an actual behavior change in a real running app that has
`image_processing` wired up -- this app's uploads would genuinely be handed
to libvips after the upgrade where they were handed to ImageMagick before.

**Unlike CIT-270, this upgrade path does leave a visible trace.** Because
this was a real in-place upgrade (not a fresh `rails new`), `bin/rails
app:update` actually ran and diffed as `M config/application.rb` (the
`load_defaults` line itself) plus a **new file**,
`config/initializers/new_framework_defaults_7_0.rb`, containing:

```ruby
# Rails.application.config.active_storage.variant_processor = :vips
```

commented out, exactly as CIT-270 predicted from the generator template
source (`new_framework_defaults_7_0.rb.tt`) without being able to observe it
directly. So the honest finding is a asymmetry within an asymmetry: the
*default* flip happens automatically and silently regardless of whether
`app:update` runs (the moment `load_defaults 7.0` takes effect, tested here
via `bin/rails runner`); `app:update`'s generated file is a **passive
breadcrumb**, not a warning -- it's committed to version control commented
out, easy to skim past in a PR diff of dozens of touched files, and does
nothing to alert a reviewer that libvips (not ImageMagick) is now the thing
parsing untrusted uploads for an app that was never audited against that
threat model. Compare to CIT-270's finding of *zero* trace on a fresh app --
this fixture shows the *realistic* upgrade path still under-communicates the
change, just not as totally as CIT-270's synthetic comparison suggested.

## Does this reach the vulnerable configuration?

Closer than CIT-270, but still short of demonstrating CVE-2026-66066 itself.
This fixture's `after` image has libvips actively processing uploads via a
real, live `variant_processor = :vips` -- the precondition CIT-270 couldn't
produce. What's still missing for an actual CWE-1188 finding: this fixture
never feeds it an untrusted/malicious upload, and doesn't inspect whether
Active Storage's libvips loader options include the untrusted-input
hardening flags the real fix added (that's CIT-272's job -- the libvips
untrusted-flag release itself, commit eba9ec0 -- not this fixture's). What
this fixture does establish, that CIT-270 couldn't: an app upgrading in
place with image processing already live gets silently switched onto the
vulnerable-at-the-time code path (vips, pre-hardening), with only a
commented-out, easy-to-miss note as any indication.

## For CIT-271/275

- `generated-apps/before/` and `generated-apps/after/` are the `files` a
  fixture can hand to a free agent or Jev -- and unlike CIT-270's trees,
  this pair actually contains the config changes (`application.rb`,
  `new_framework_defaults_7_0.rb`) that a reviewer would need to notice.
- `restic-diff-before-to-after.txt` is the `diff_items` source. Its much
  smaller size (3,162 vs. CIT-270's 13,489 lines) and the fact that the
  `changed` (not just new/removed) file list is short and meaningful means
  this is a *cleaner* signal for CIT-271's free agent than CIT-270's diff --
  worth considering as the primary `state` source for
  `fixture-active-storage.json` instead of (or alongside) CIT-270's, since
  its `state_source` placeholder currently says "CIT-270 snapshot diff." Not
  changing that file in this pass -- flagging it as a decision for whoever
  runs CIT-275, since picking the *cleaner* diff also makes the hint ladder
  slightly easier, which is a real tradeoff, not a strict improvement.
- The `new_framework_defaults_7_0.rb` file is the single most
  loadbearing piece of `state` for testing whether a free agent or Jev
  actually reads a commented-out line rather than skimming past it -- worth
  flagging explicitly in whatever prompt CIT-275/271 construct.
