## 1. What the inspection found

1. **No step of the 117 → 118 → 120 history is a working interaction today.** It exists as
   recorded data (git, Linear text, PR text, committed reports) and one static TutorialKit page.
   The components that could drive it exist, but as Storybook fragments or read-only replay panes.
2. **The recorded history has four review rounds; the only lesson tells three.** Its "Round three"
   says a deleted or forged trace now changes what is computed. The fourth round (`cc23e89`) found
   that after `296ca9f` deleting a blocked arm's whole trace, or forging a prose mention, a failed
   open or a same-named file in another directory, still passed. The lesson overstates what the
   third round achieved (§6, T10).
3. **The reviews are in Linear, not GitHub, and cite pre-rebase commits.** GitHub holds no review
   on #117, #118 or #120 and no comment except Netlify's. The Linear review text cites `20aafd2`
   and `8d097c8`; `main` contains `390a787` and `9739b53`. Each pair has the same author time and
   the same `git patch-id`, so they are the same patches on a different parent.
4. **The evidence for the review findings was not retained.** The reviewers' mutation runs were done
   in temporary copies and their output was not kept. The third review's text could not be retrieved
   from GitHub or Linear; it is known only through a commit message and the write-up. The findings are *recorded
   prose*, not captured executions.
5. **The authoring behaviours closest to the CIT-304 vision are Storybook-only.** Typing claims with
   live diagnostics and legal-world counts (Follower Maze) and registration (Precog Board) are
   mounted by no TutorialKit lesson. TutorialKit's own typing loops are the older labs (Schadenfreude
   and Fingerspitzengefühl, the German sentence repair, the capability labs); they type an answer, a
   sentence or a declaration, not a question. Registration is a stub. **Grey suggestions, and
   selecting premises or commits to explore alternatives, do not exist anywhere.**
6. **"Done" does not mean the stories pass.** 9 of the 47 Storybook stories fail at this revision,
   deterministically (§8).

## 3. Vocabulary

Implementation, evidence and row status are tracked separately, so a working interaction can show
recorded evidence.

| Column | Values |
| --- | --- |
| Implementation | **working** (runs and responds today) · **stubbed** (renders, but input or data is fixed) · **missing** |
| Evidence | **captured execution** (output of a real run) · **live computation** (a real checker run in the browser over a fixture) · **recorded prose** (real review or PR text, not an execution) · **authored illustration** (hand-written; labelled as such) · **not available** |
| Row status (the issue's terms) | **working** · **recorded replay** · **missing** |
| Disposition | **reuse** · **adapt** · **missing** · **deliberately deferred** |

"Recorded prose" is added to the three evidence classes suggested in the CIT-304 thread: a review
is real and dated, but it is not an execution, and the table must not blur the two.

### Invariants to preserve

- Input, monitor, diagnostic and each verdict channel stay separate; a model score, an executed check
  and an authority decision never share one pass/fail badge.
- Recorded, scripted and simulated material keeps its label; nothing invents a timestamp, trace link or
  Git hash that was not recorded.
- The original failure stays visible after a repair, and a pin is never edited, only superseded.
- Typed input becomes typed records; nothing downstream compares strings to an expected reason.
- "Not scored" or "pending" is shown before a recorded result is revealed.
- Absence is shown as absence ("not captured"), never filled in.
- The viewer observes a recorded turn; navigation must not look like an agent action (CIT-251, CIT-298).

### Notes on the table

**Deferral.** T11, T12, I12 and I13 are out of CIT-306's first walkthrough. If anything is shown for
them, the reader's addition is labelled post hoc, carries no seal and no "prediction" styling, and is
never placed before the run it asks about. The Precog Board's sealed/predicted visuals are not reused
for it. A new question asked while inspecting old evidence is not a prediction recorded before that
historical run.

**Revision identity.** A deep link into this history must say whether it means the reviewed commit
(`20aafd2`, `8d097c8`) or the merged one (`390a787`, `9739b53`). Both pairs resolve from `origin` by
hash; only the merged ones are on `main`.

**Evidence for the findings (T3, T5, T7).** The options are to show them as recorded prose with
captured execution marked *not available* (cheapest, and accurate), or to re-run the named mutations
against S1, S2 and S3 and label the result "re-executed now, not at review time". The second needs
`pkl` and is not in CIT-306's first slice (§7, U5).

**What the lead case supports.** (1) One live run showed disclosure when unblocked, a specific
refusal when blocked, and PNG processing unaffected (captured; not re-run here). (2) The final
checker catches the mutations the three reviews named (committed tests and reports; not re-run
here). (3) Each round's claim of closure was tested by the next review, and twice it did not hold.
It does **not** support: that the MATLAB blocking control is secure in general; any claim about clean-merge
composition; that a model or Jev found the issue unprompted (out of scope per CIT-294); or that the
findings were reproduced from retained artifacts at review time.
