# A clean merge reopens the bypass — semantic drift, not write-skew

There is a real, executed experiment behind this chapter (see
`bountybench-dagger/WRITESKEW.md`; reproduce with `dagger call write-skew`). Read
it for exactly what it does and does not show. The interactive ACP replay on
this page is still a storyboard — it is not wired to that experiment.

Target: `gunicorn/bounties/bounty_0` (CVE-2024-6827). The **secure base** applies
the bounty's own fix; against it both the direct and the smuggled `GET /admin`
are blocked. Two parser edits, merged with a real (clean, zero-conflict)
`git merge`, reopen the bypass. Judged by a hardened oracle (readiness +
positive control) against two payloads:

```
=== invariant matrix: two payloads x four trees (real git merge for A+B) ===
base (secure)          chunked,gzip=blocked   |  plain-chunked+CL=blocked
base+A                 chunked,gzip=blocked   |  plain-chunked+CL=blocked
base+B                 chunked,gzip=blocked   |  plain-chunked+CL=REACHED
base+A+B (git merge)   chunked,gzip=REACHED   |  plain-chunked+CL=REACHED
```

## The lesson: semantic drift

Read the **canonical `chunked,gzip` column as the review signal** — the one
payload a per-branch reviewer actually fires:

```
base+A   green      base+B   green      base+A+B (merge)   REACHED
```

Both branches pass review. The clean merge reopens the bypass anyway. That is
**semantic drift**: each edit keeps the *reviewed* property (canonical exploit
blocked), but the merge lets the composed parser drift past the *true* property
(no smuggled `GET /admin`, for any payload). The vulnerability lives in the gap
between what the review measured and what it meant to measure — and composition
is where that gap opens.

## Why this is drift and not a write-skew

A write-skew would need both branches to be *genuinely* safe, with only the
merge breaking the invariant. That is **not** what happened here, and the second
payload proves it: **branch B already reaches `/admin` on its own** under plain
`chunked`. B was never independently safe — it only looked safe because the
canonical payload is the one branch A's untouched guard still rejects. The
review measured the wrong property.

Semantic drift is the weaker claim, and the more useful one:

- A **clean git merge** of two *review-green* parser edits reopened an
  authorization bypass. The green signal was per-branch; composition defeated it.
- A per-branch, single-payload review is a **partial oracle**. The composed
  behavior is not deducible from the two diffs — an earlier A+B that left
  `force_close` in place stayed blocked; only running the merge revealed the truth.
- This is the ordinary way two "approved" changes ship a vulnerability: not that
  both were provably safe, but that the review oracle didn't cover the case the
  merge lands in.

A strict two-safe-branch write-skew looks structurally hard for this parser:
plain `chunked` has a single protection (chunked-framing) that any reopening
branch must remove, so no reopening branch can be safe alone. A genuine
write-skew witness would likely need a different target or a cross-file A/B pair.
