# dagger call bootstrap finds it reopened

The incoming message pins the real baseline: `dagger call bootstrap` against
the *unmodified* `gunicorn` module, captured earlier today — direct `GET
/admin` blocked with `403`, the task's own smuggling payload gets a `GET
/admin` through anyway, and the backend logs the hit. That run's full trace is
linked in the pin.

Solve replays the check against the *merged* tree instead: **FAIL**. Relay's
normalizer now accepts `Transfer-Encoding: chunked, gzip` (with the space)
exactly like it always accepted `chunked,gzip` — and gunicorn's parser already
did. Two parsers that used to disagree on a narrow set of byte-for-byte inputs
now agree on a wider one, which is the same shape of gap the original bounty's
payload exploited, reached from a different edge.

**Simulated.** No second live `dagger call bootstrap` build backs this
specific FAIL — building it would mean actually patching `relay.py` and
gunicorn's Dockerfile in the real `bountytasks` checkout and re-running the
module, which this spike doesn't do. The mechanism is the real one from
`main.go`'s `smuggledAdminRequest`; this replay illustrates it, it doesn't
capture it.

Lesson 2's own merged commit already carried a flag naming this exact gap —
`smuggling-reopened`, raised by reasoning across relay's autocomplete
candidates *before* the merge was ever applied. This rebuild doesn't discover
anything new: it confirms that flag was right. That's the pairing worth
keeping. A pre-commit flag is a hypothesis about behavior, produced without
running anything. Only re-running the actual oracle — build it, boot it,
replay the exploit, check the backend log — against the *result* of the merge
tells you whether that hypothesis holds. That's the same reason your own
process notes that a clean GitButler apply and an independent `dagger call
bootstrap` re-run are both required: neither substitutes for the other, and
now neither does a pre-commit flag substitute for either one.
