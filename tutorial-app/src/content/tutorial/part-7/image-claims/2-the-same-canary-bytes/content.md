# A PNG that isn't one

A **canary** is a specially crafted test file: harmless itself, but built so
that a mistake in how it is handled shows up. This one was crafted for a Rails
investigation. A **loader** is the component that interprets a file's bytes;
here, libvips (the image library Rails uses for variants) and matio (a library
for MATLAB files) are the two loaders that matter.

Everything about the canary except its bytes says PNG:

| What | Says |
| --- | --- |
| File name | `rails-canary.png` |
| Declared upload type | `image/png` |
| First 8 bytes | `MATLAB 5`, not the PNG signature `\x89PNG\r\n\x1a\n` |
| Text header | `MATLAB 5.0 MAT-file`, which makes libvips choose its MATLAB loader |
| Version and endian bytes (offset 124) | `00 02` and `IM`, which make matio read it as a MAT 7.3 (HDF5) file |

In the original investigation, an upload declared `image/png` reached libvips'
MATLAB loader. libvips and matio each acted on a different part of that
header. The resulting HDF5 read returned bytes from a test-owned dummy file
through a Rails image variant.

The **control** is an ordinary comparison input: in the Rails runs, a real PNG
sent through the same steps. Whatever the canary does that the control doesn't
is the effect of its bytes.

**Provenance.** These are the investigation's canary bytes, regenerated by its
`craft_mat_canary.py`. Their SHA-256,
`f1c62ebc5fb7ab50655d505f3c30498713cdef232d3bdef585935024bd007fcc`, matches
both retained MATLAB runs. Renaming the file changes neither.
