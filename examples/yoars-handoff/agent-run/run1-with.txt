## How report.py must treat what comes out of `normalize()`

**Kept lines.** You get a dict `{ident, person, worth, moment, variety, group}`:
- Use `worth` as the value to sum. It's a float that has already been unit-cleaned and rounded to 2dp. Don't rescale it.
- `moment` is an int.
- Group by `group`, which is always one of `retail`, `food`, `travel` or `other`. `variety` can be a str or an int, so don't key on it.
- Only `group` and `worth` are needed for the summary. Read nothing else from the record.

**Dropped lines.** `normalize()` returns `None` for:
- a `person` starting with `test-`;
- a `moment` below 1700000000, including a missing or non-numeric one, which becomes 0.

Skip these entirely. They count toward nothing: not totals, not counts, not groups. In probe P4, that's EV-401 (`test-bot`) and EV-402 (`1699999999`).

There's a third case the handoff leaves out. A line that passes the drop checks but has an empty or non-numeric `worth` makes `float()` raise instead of returning `None`. It isn't a drop. report.py shouldn't quietly swallow it, because a swallowed exception turns a wrong count into a pass. Let it fail, or flag it to backend.

**Worth for each unit label.** The scaling happens in `normalize`, not in report.py:

| `gauge` from parse | Source | What normalize does |
|---|---|---|
| `hundredths` | every pipe line; pair `u=C` | ÷100, round 2 |
| `plain` | pair `u=E` | unchanged, round 2 |
| `thousandth` | JSON `scaled:true`, **only if auth uses exactly this string** | ×1000, round 2 |
| `thousandth-scale` or anything else | possibly JSON `scaled:true` (auth's docstring name) | **unchanged, no error** |
| `""` | pair with a `u` other than E/C; possibly JSON | unchanged, no error |

## What report.py should assume for each unit label

- **`hundredths`**: safe to trust. Both the parse code and the transform code are visible and agree.
- **`plain`**: safe to trust.
- **`thousandth`**: only correct if auth's JSON branch emits exactly that string. That hasn't been checked; it's the part cut from #34.
- **anything else, including `thousandth-scale` and `""`**: treat as unresolved, not as plain. Today it passes through unscaled with no error. P3 and P5 (`scaled:true`: 3.75 should become 3750, 2.00 should become 2000) would come out wrong by a factor of 1000.

report.py shouldn't fix this by rescaling on its own side. That would apply backend's rule in the wrong stage. It also can't see `gauge`, because normalize doesn't return it.
