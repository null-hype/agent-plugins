# Testing devcontainer Features

Use the upstream [testing guide](reference/devcontainers-cli-features-test.md)
for `devcontainer features test`. The pinned reference records the source URL
and retrieval revision. Check `devcontainer features test --help` for the
installed CLI's current flags.

## Choose the test location

| Test | Files | Purpose |
| --- | --- | --- |
| Default installation | `test/<feature>/test.sh` | Install that feature at default options on the selected base image. |
| Feature scenario | `test/<feature>/scenarios.json`, `<name>.sh` | Test options or a combination of features owned by that feature. |
| Global scenario | `test/_global/scenarios.json`, `<name>.sh` | Test a combination that is not owned by one feature. |
| Duplicate installation | `test/<feature>/duplicate.sh` | Test two installations with differing options when relevant. |

A scenario key matches its shell script name. Its value is a devcontainer
configuration snippet: `image` or `build`, `features`, and other standard
devcontainer properties. A feature-local scenario may install several features;
it does not need to move to `_global` just because it has dependencies.

## Run the installed feature

The CLI builds and starts the container, then executes the matching shell
script. Use the installed application, commands, and contracts in that script.
The CLI's helper is optional; the usual repository pattern is:

```bash
#!/bin/bash
set -e
source dev-container-features-test-lib
check "installed command works" my-command --help
reportResults
```

Tests can invoke a scenario's Python test or `pkl test` directly. Consume Pkl
types through the existing language bindings; keep Pkl's `.pkl-expected.pcf`
goldens beside the Pkl tests. There is no need for a separate experiment runner
or a duplicate JSON answer key.

The CLI mounts the test script directory into the container (`SCRIPT_FOLDER`
in the helper). Keep test fixtures there or create them at runtime. It does not
mount the entire repository. If a scenario needs additional image build files,
put them in `test/<feature>/<scenario-name>/` and reference its `Dockerfile`
through `build`. The CLI copies that directory into the intermediate build
context; the Dockerfile must copy files needed in the image.

## Run tests

```bash
# Default installation only, on a chosen image.
devcontainer features test -f noteexpand -i ubuntu:latest --skip-scenarios --skip-duplicated .

# The feature's declared scenarios (including noteexpand + Jev).
devcontainer features test -f noteexpand --skip-autogenerated --skip-duplicated .

# Global combinations.
devcontainer features test --global-scenarios-only .
```

CI uses these same commands. Add a new feature to the existing feature matrix
and put its scenarios in the conventional location, rather than filtering or
rewriting `scenarios.json` in CI.

A passing container test requires both a successful build/start and a script
exit status of zero. Host checks can validate logic and types, but do not prove
installation. State which actually ran. If Docker is unavailable locally, use
the container CI results as installation evidence.
