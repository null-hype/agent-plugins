# Testing devcontainer Features

Operational rules for testing the Features under `src/` with the devcontainer
CLI. The verbatim upstream guide this is distilled from is pinned at
[`reference/devcontainers-cli-features-test.md`](reference/devcontainers-cli-features-test.md)
(source URL, revision and retrieval date in its header). This file is the
operating manual; the pinned copy is the citation. When they disagree, the CLI's
own `devcontainer features test --help` wins — this repo installs the unpinned
`latest` CLI (see `.github/workflows/test.yaml`), so re-check flags there before
assuming.

## Read-before-edit contract

If your assignment told you to load this skill: before editing any Feature,
`test/<feature>/` file, or `test/_global/` file, **read this whole file and then
state, in your working notes or PR text, which numbered rules below you are
applying and how.** A change that touches these paths without naming the rules
it followed has not applied the skill. The acceptance checklist at the bottom is
the minimum bar.

## How `devcontainer features test` actually runs (why "it passed" needs proof)

`devcontainer features test [.]` **builds a real dev container image, starts a
container, and execs a test script inside it.** A test passes only if BOTH (1)
the container builds and starts, AND (2) the script exits 0. This is the only
thing that establishes that a Feature *installs and works in a container*.

Therefore (Rule V — verification honesty):

- **V1.** Running a Feature's `install.sh`, its `evidence-validate`/`jev` bin, or
  a `.sh` scenario body **on the host** (or under a stubbed
  `dev-container-features-test-lib`) checks *logic*, not *installation*. Never
  report host/logic checks as "the container test passed." Say exactly what ran:
  "ran the check logic on the host (no container)" vs. "`devcontainer features
  test` built and started the container and the script exited 0."
- **V2.** If Docker is unavailable where you are, you cannot satisfy (1). Wire the
  scenario correctly and run it in CI (`.github/workflows/test.yaml` runs
  autogenerated + feature scenarios on push/PR; `test-global.yaml` runs every
  scenario, feature-local and global, on manual `workflow_dispatch`). Record the
  CI run (or the specific blocker) as the container evidence — do not claim a
  local pass you did not get.
- **V3.** A green *deterministic* run does not mean the *live* method works. Keep
  the two kinds of evidence separate in every report (see Rule M).

## The four test modes

1. **Auto-generated** (`test/<feature>/test.sh`). The CLI builds a container with
   the Feature at **default options** and execs `test.sh`. Assert the Feature's
   installed commands from inside that container (e.g. `check "jev on PATH" bash
   -c "jev --help >/dev/null"`). Run just this mode with `--skip-scenarios
   --skip-duplicated`. Every Feature must have a passing `test.sh`.
2. **Scenarios** (`test/<feature>/scenarios.json` + a `<name>.sh` per key). A
   scenario is a `devcontainer.json` snippet keyed by test name — use it to test
   non-default **options** or **more than one Feature** in one container. The CLI
   builds each scenario and execs the matching `<name>.sh`. Run with
   `--skip-autogenerated --skip-duplicated`.
3. **Global scenarios** (`test/_global/scenarios.json` + a `<name>.sh` per key).
   Same shape as feature scenarios but not tied to one Feature — this is where
   **combinations of Features** are tested (e.g. `evidence` + `jev` in one
   container). Run with `--global-scenarios-only`.
4. **Duplicate-install** (`test/<feature>/duplicate.sh`). The CLI installs the
   same Feature twice with different options; the option values arrive as env
   vars (`FOO`, `FOO__DEFAULT`). Use it to prove a Feature is idempotent /
   installs twice without conflict. Add one only when a Feature can plausibly be
   installed more than once; skip otherwise.

Rule T (test the installed thing): **Assert the command/file the Feature
installs, inside the built container** — `command -v <bin>`, `<bin> --help`,
`test -f "$HOME/.claude/skills/<name>/SKILL.md"`, a real invocation. Do not
assert against a copy of the source tree or a host path.

## Self-contained scenarios (Rule S)

The scenario `.sh` runs **inside the generated container/workspace**, not in your
checkout. It can see only what the base image ships, what the Features installed,
what a scenario build file baked in, and what the script itself creates at
runtime.

- **S1.** Do **not** read checkout-relative paths (e.g. `docs/method/toy-case/...`,
  `../../src/...`) from a scenario script. They are not present in the container.
- **S2.** Generate fixtures at runtime with heredocs into a `mktemp -d` (see
  `test/jev/test.sh` and `test/evidence/test.sh` for the pattern), OR bake them
  in via a scenario build file.
- **S3.** Scenario build files go in `test/<feature>/<scenario-name>/` (or
  `test/_global/<scenario-name>/`) and are copied into the generated hidden
  `.devcontainer`. Reference them with `"build": {"dockerfile": "Dockerfile"}` in
  the scenario. A `Dockerfile` there must `COPY` anything the running script
  needs into the image — being in the build context is not the same as being on
  the container's filesystem at test time. If a scenario needs the toy case,
  **copy the toy files into that scenario's own dir**; never point at `docs/`.

## Method contract: reasoning model → Jev (Rule C, from CIT-286)

The method pipeline is: a reasoning agent emits an **evidence file** →
`evidence-validate` (Pkl format check + grounding) → only if valid, the **`jev`** client
sends the fixture `state` to the Noul judge and returns one probability in
`[0,1]` per question. Hint level is a *runtime parameter*, not a scenario (Rule
D3). The contract scenarios to maintain:

- **C1 — format.** Agent output validates against the Pkl evidence
  definition (`src/evidence/pkl/Evidence.pkl`; Pkl is authoritative, Python is
  only the adapter). An empty `{"findings":[]}` ("no
  findings") is **valid** and must stay valid.
- **C2 — grounding.** Every `excerpt` appears **verbatim** at its `source_path`
  under the image root (`evidence-validate --root <root>`); a path escaping the
  root, a missing file, or a symlink out of the root is rejected.
- **C3 — isolation.** The reasoning run's init event shows filesystem tools and
  **no web tools**. Check an actual recorded init event in the runner
  tests (CIT-271); an adapter-generated declaration does not prove containment.
- **C4 — Jev accepts.** Given valid evidence/state and Noul questions, `jev`
  returns exactly the input question ids, each a finite number in `[0,1]`.
  Out-of-range or non-finite answers are rejected; probabilities are never
  invented (mock needs `--mock-answers`; real needs `TYPESAFE_API_KEY`).
- **C5 — reject before Jev, observably.** Malformed **or** ungrounded evidence is
  rejected **before `jev` is invoked at all**. The test must make Jev-invocation
  *observable* (e.g. a PATH shim or wrapper that records each call) and assert the
  call count is **0** on the reject path and **≥1** on the accept path. A test
  that only checks the final exit code does not prove the seam.

Define the record types and case checks in Pkl and consume them through the
existing language bindings. Generate consumer types from the owning module;
do not maintain handwritten Python copies or custom subprocess/JSON evaluators.
Use lesson 5 (`part-1/chapter-3/lesson-5`) end to end: independent records of the
same event, a domain check over those records, and a compare-and-record matcher.

Each global `.sh` invokes its own `<scenario>_test.py` directly. Case-specific
checks and expectations stay with the case. Capture the exact Jev request and
raw response; preserve evidence, observed state and diagnostics in a fresh run
directory. Append evaluations on pass and fail, and upload records even on
failure. A correctly detected disagreement may be the expected test result.

Do not replace a domain check with a generic confidence classification. Keep
Jev's numeric response. Any confidence predicate belongs to the experiment that
explicitly declares it; supply no default score ordering or thresholds.

## Deterministic vs. live execution (Rule M)

- **M1.** Default test entry points use recorded evidence and mock Jev. They run
  without model credentials and never select live execution from credentials.
- **M2.** Put actual collection/real Jev in a separate, explicitly invoked live
  entry point and a manual workflow. Caller supplies authentication and runner
  isolation; preserve the runner init event and trace. Do not add a generic
  mode/spend-policy engine to the contract library. Never put keys in argv.
- **M3.** Report deterministic tests and live observations separately. A mock
  response cannot establish model discrimination, calibration or containment.

## Dependency direction (Rule D, from CIT-265)

Keep case data out of reusable equipment. Violating this contaminates the
experiment.

- **D1 — equipment** (`pass-cli`, `playwright-cli`, `tailscale`, the runner):
  no evidence/Jev/CVE knowledge.
- **D2 — reusable method Features** (`src/evidence`, `src/jev`): the *format*,
  *validator*, and *client* only. **No Rails/CVE case data, no CVE-specific
  prompts, constants, or hint sweeps** may enter these Features or their
  `test.sh`. `jev`'s `state` stays opaque; it must not assume the evidence shape.
- **D3 — experiments** (`docs/method/toy-case`, the Dagger case modules, and
  scenario-local fixtures): supply case data and runtime parameters. **Hint
  level, model, and repeats are experiment parameters**, expressed as scenario
  options / fixture fields / env — never as separate method contract scenarios.
- **D4 — answer keys stay out of the inspected filesystem.** Expected evidence,
  control labels, `expected.rationale` (the real CVE name), and any `meta`/
  `expected` block must live **outside** the image root the agent reads and
  **must not** reach the model. `jev` already drops everything but `.state`; keep
  fixtures shaped so the harness-only material never lands under the agent-visible
  root.

## Acceptance checklist (what "done" means)

- [ ] You read this skill and named the rules you applied (read-before-edit).
- [ ] New/changed Feature has a passing `test/<feature>/test.sh` that asserts the
      installed command **inside the container** (Rule T), self-contained (Rule S).
- [ ] Feature/global scenarios are self-contained (Rule S) — no `docs/`- or
      checkout-relative reads from a scenario script.
- [ ] Contract scenarios cover C1/C2/C4/C5, with Jev-invocation **observable**
      and asserted 0-on-reject / ≥1-on-accept; C3 belongs to actual runner tests.
- [ ] Pkl owns types/checks and existing bindings load them; scenario tests
      directly use mock Jev. Live execution has a separate entry point.
- [ ] Records connect the claim, independent observation, actual model input and
      response to the case check; there is no invented global confidence rule.
- [ ] No CVE/case data, prompts, constants, or hint sweeps entered `src/evidence`
      or `src/jev` (Rule D); answer keys/labels stay out of the inspected root (D4).
- [ ] The container evidence is a real `devcontainer features test` run (local or
      CI); host/logic-only checks are reported as such, never as a container pass
      (Rule V).
